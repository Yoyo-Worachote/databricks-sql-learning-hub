## ข้อมูลใน Databricks จัดเก็บอย่างไร

ให้นึกถึงข้อมูลใน Databricks เหมือน **ตู้เอกสาร** ที่จัดเป็นชั้น ๆ

| ระดับ | ความหมาย | เปรียบเทียบ | ตัวอย่างในหลักสูตร |
|---|---|---|---|
| **Catalog** | กลุ่มใหญ่สุดของข้อมูล | ห้องเก็บเอกสาร | `main` (ขึ้นกับองค์กร) |
| **Schema** (บางระบบเรียก **Database**) | กลุ่มของตารางที่เกี่ยวข้องกัน | ตู้เอกสาร 1 ตู้ | `sql_training` |
| **Table** | ตารางข้อมูล 1 ตาราง | แฟ้ม 1 แฟ้ม | `sales`, `products` |
| **View** | Query ที่บันทึกชื่อไว้ เรียกใช้เหมือนตาราง แต่ไม่ได้เก็บข้อมูลซ้ำ | ใบสรุปที่คำนวณใหม่ทุกครั้งที่เปิด | `v_sales_daily` (บทที่ 20) |

**ชื่อเต็มของตาราง** ใน Workspace ที่ใช้ Unity Catalog มี 3 ระดับ คือ `catalog.schema.table` เช่น `main.sql_training.sales`

ถ้าเลือก Catalog และ Schema เริ่มต้นไว้แล้ว (ผ่าน Dropdown ใน SQL Editor หรือคำสั่ง `USE`) จะเขียนแค่ `sales` ได้เลย

```sql
USE sql_training;
```

> [!NOTE] Workspace รุ่นเก่า
> Workspace ที่ยังไม่ได้ใช้ Unity Catalog จะใช้ Catalog ชื่อ `hive_metastore` และมักเขียนชื่อตาราง 2 ระดับ คือ `schema.table` เช่น `sql_training.sales`

## Row, Column และชนิดข้อมูล

ตารางในฐานข้อมูลหน้าตาเหมือนชีตใน Excel

- **Row (แถว)** = ข้อมูล 1 รายการ เช่น การขายสินค้า 1 รายการในบิล
- **Column (คอลัมน์)** = คุณสมบัติของรายการ เช่น วันที่ขาย รหัสสาขา จำนวนชิ้น

ตัวอย่างแถวจากตาราง `stores`: แต่ละแถวคือ 1 สาขา แต่ละคอลัมน์คือข้อมูลของสาขานั้น

| store_id | store_name | region | open_date |
|---|---|---|---|
| S01 | สาขาสุขุมวิท | Bangkok | 2019-05-01 |
| S03 | สาขาเชียงใหม่ | North | 2021-03-01 |

ทุกคอลัมน์มี **ชนิดข้อมูล (Data Type)** ที่กำหนดว่าเก็บค่าแบบไหนได้ ชนิดข้อมูลมีผลต่อการกรอง เรียง และคำนวณ

| ชนิดข้อมูล | เก็บอะไร | ตัวอย่างค่า | วิธีเขียนค่าใน SQL |
|---|---|---|---|
| `STRING` | ข้อความ | `S01`, `Cash` | ใส่ใน `' '` เช่น `'S01'` |
| `INT` | จำนวนเต็ม | `3`, `-2` | เขียนตรง ๆ เช่น `3` |
| `DECIMAL(10,2)` | ตัวเลขทศนิยม (ตัวเลขรวม 10 หลัก ทศนิยม 2 ตำแหน่ง) | `18.00` | `18.00` |
| `DATE` | วันที่ | `2026-02-14` | `DATE'2026-02-14'` |
| `TIMESTAMP` | วันที่และเวลา | `2026-02-14 15:54:17` | `TIMESTAMP'2026-02-14 15:54:17'` |
| `BOOLEAN` | จริง/เท็จ | `true`, `false` | `TRUE`, `FALSE` |

> [!WARNING] ระวังวันที่หรือตัวเลขที่เก็บเป็นข้อความ
> ถ้าวันที่ถูกเก็บเป็น `STRING` เช่น `'05/01/2026'` ระบบจะเรียงและเปรียบเทียบแบบตัวอักษร ไม่ใช่แบบวันที่ ต้องแปลงชนิดก่อน (บทที่ 17–18)

## รู้จักชุดข้อมูลฝึก

ทุกบทใช้ข้อมูลจำลองของร้านค้าปลีกสมมติที่มี 6 สาขา และสินค้า 12 รายการ อยู่ใน Schema `sql_training`

| ตาราง | 1 แถว หมายถึง | จำนวนแถว | ใช้ฝึกเรื่อง |
|---|---|---|---|
| `sales` | สินค้า 1 รายการในบิล (ม.ค.–มี.ค. 2026) | 141 | แทบทุกบท |
| `products` | สินค้า 1 ตัว | 12 | JOIN, กำไรขั้นต้น |
| `stores` | สาขา 1 แห่ง | 6 | JOIN, ภูมิภาค |
| `promotions` | โปรโมชัน 1 รายการ (สินค้า 1 ตัวมีได้หลายโปรฯ) | 4 | JOIN หลายเงื่อนไข, Fan-out |
| `calendar` | วันที่ 1 วัน (ต.ค. 2025 – มี.ค. 2026) | 182 | ยอดขายรายวันครบทุกวัน |
| `sales_archive_2025` | เหมือน `sales` แต่เป็น ต.ค.–ธ.ค. 2025 | 50 | UNION ALL, เทียบช่วงเวลา |
| `sales_raw` | แถวจากไฟล์ Excel ดิบ (ทุกคอลัมน์เป็นข้อความ) | 8 | แปลงวันที่/ตัวเลข, ทำความสะอาด |

**ความสัมพันธ์ระหว่างตาราง** (ใช้ตอน JOIN ในบทที่ 10)

| คอลัมน์ในตารางหลัก | เชื่อมกับ | ความหมาย |
|---|---|---|
| `sales.store_id` | `stores.store_id` | รายการขายนี้เกิดที่สาขาไหน |
| `sales.product_id` | `products.product_id` | รายการขายนี้เป็นสินค้าอะไร |
| `promotions.product_id` | `products.product_id` | โปรโมชันนี้ใช้กับสินค้าอะไร |
| `sales.sale_date` | `calendar.cal_date` | รายการขายนี้อยู่วันไหนในปฏิทิน |

ดูโครงสร้างและข้อมูลตัวอย่างของทุกตารางที่ [หน้าชุดข้อมูลฝึก](#/reference/dataset)

## โครงสร้างตาราง sales (ตารางหลัก)

| Column | ชนิดข้อมูล | คำอธิบาย |
|---|---|---|
| `sale_id` | STRING | เลขที่รายการขาย |
| `sale_date` | DATE | วันที่ขาย |
| `sale_datetime` | TIMESTAMP | วันและเวลาที่ขาย |
| `store_id` | STRING | รหัสสาขา (เชื่อมกับ `stores`) |
| `product_id` | STRING | รหัสสินค้า (เชื่อมกับ `products`) |
| `customer_id` | STRING | รหัสลูกค้าสมาชิก (`NULL` = ไม่ใช่สมาชิก) |
| `quantity` | INT | จำนวนชิ้น (ติดลบ = รับคืน) |
| `unit_price` | DECIMAL(10,2) | ราคาขายต่อชิ้น (หลังโปรโมชัน) |
| `discount_amount` | DECIMAL(10,2) | ส่วนลดท้ายบิล (`NULL` = ไม่ได้บันทึก) |
| `net_amount` | DECIMAL(12,2) | ยอดขายสุทธิ = quantity × unit_price − ส่วนลด |
| `payment_method` | STRING | วิธีชำระเงิน: Cash / Credit Card / QR Payment |

> [!TIP] อ่านคำอธิบายคอลัมน์ทุกครั้ง
> คำอธิบาย (comment) มักบอกความหมายทางธุรกิจที่สำคัญ เช่น `quantity` ติดลบหมายถึงรับคืน หรือ `customer_id` ที่เป็น `NULL` หมายถึงลูกค้าทั่วไปที่ไม่ใช่สมาชิก

## สำรวจตารางด้วย SHOW TABLES และ DESCRIBE

ก่อนเขียนรายงาน ให้สำรวจข้อมูลก่อนเสมอ 3 คำสั่งแรกที่ควรใช้คือ

```sql
SHOW TABLES IN sql_training;
```

| namespace | tableName | isTemporary |
|---|---|---|
| sql_training | calendar | false |
| sql_training | products | false |
| sql_training | promotions | false |
| sql_training | sales | false |
| sql_training | sales_archive_2025 | false |
| sql_training | sales_raw | false |
| sql_training | stores | false |

`SHOW TABLES IN sql_training` แสดงรายชื่อตาราง (รวม View) ใน Schema ที่ระบุ ถ้าไม่ระบุ `IN ...` จะแสดง Schema ที่ตั้งเป็นค่าเริ่มต้น หัวคอลัมน์แรกอาจชื่อ `database` หรือ `namespace` ขึ้นกับเวอร์ชัน

> [!NOTE] ตารางเสริมของเว็บไซต์
> ถ้ารันไฟล์ `practice_extra_tables.sql` ของเว็บไซต์นี้ด้วย จะเห็นเพิ่มอีก 3 ตาราง คือ `store_product`, `monthly_sales` และ `customers` (ดูหน้าชุดข้อมูลฝึก)

```sql
DESCRIBE TABLE promotions;
```

| col_name | data_type | comment |
|---|---|---|
| promo_id | string | รหัสโปรโมชัน |
| product_id | string | รหัสสินค้า |
| promo_name | string | ชื่อโปรโมชัน |
| start_date | date | วันเริ่ม |
| end_date | date | วันสิ้นสุด (รวมวันนี้ด้วย) |
| discount_pct | int | เปอร์เซ็นต์ส่วนลด |

`DESCRIBE TABLE` แสดงชื่อคอลัมน์ (`col_name`) ชนิดข้อมูล (`data_type`) และคำอธิบาย (`comment`) ถ้าต้องการข้อมูลละเอียดขึ้น เช่น ตำแหน่งเก็บไฟล์และเจ้าของตาราง ใช้ `DESCRIBE TABLE EXTENDED promotions;`

## ดูตัวอย่างข้อมูลด้วย LIMIT และนับแถวด้วย COUNT(*)

ตารางเล็กอย่าง `stores` ใช้ `SELECT *` ดูทั้งตารางได้ แต่ตารางจริงในองค์กรอาจมีหลายล้านแถว ให้ดูตัวอย่างด้วย `LIMIT` เสมอ

```sql
SELECT *
FROM sales
LIMIT 5;
```

**ตัวอย่างผลลัพธ์** (แถวที่ได้อาจต่างจากนี้ เพราะไม่ได้ระบุลำดับ)

| sale_id | sale_date | store_id | product_id | customer_id | quantity | unit_price | discount_amount | net_amount | payment_method |
|---|---|---|---|---|---|---|---|---|---|
| T0001 | 2026-01-02 | S01 | P002 | C016 | 1 | 18.00 | 0.00 | 18.00 | Cash |
| T0002 | 2026-01-02 | S01 | P002 | C013 | 1 | 18.00 | 0.00 | 18.00 | Credit Card |
| T0003 | 2026-01-02 | S04 | P003 | C004 | 5 | 18.00 | 0.00 | 90.00 | QR Payment |
| T0004 | 2026-01-03 | S02 | P004 | C017 | 3 | 25.00 | 0.00 | 75.00 | QR Payment |
| T0005 | 2026-01-03 | S03 | P002 | C004 | 1 | 18.00 | NULL | 18.00 | Cash |

(ตารางนี้ละคอลัมน์ `sale_datetime` ไว้เพื่อให้อ่านง่าย ผลจริงจะมีครบ 11 คอลัมน์)

> [!WARNING] LIMIT ไม่ได้แปลว่า "แถวแรกของตาราง"
> ตารางในฐานข้อมูลไม่มีลำดับแถวที่แน่นอน `LIMIT` ที่ไม่มี `ORDER BY` อาจได้แถวต่างกันในแต่ละครั้งที่รัน ใช้เพื่อดูหน้าตาข้อมูลเท่านั้น

นับจำนวนแถวทั้งหมดเพื่อรู้ขนาดตาราง (ตัวเลขนี้จะใช้เทียบเมื่อกรองหรือ JOIN ภายหลัง)

```sql {verify}
SELECT COUNT(*) AS row_count
FROM sales;
```

| row_count |
|---|
| 141 |

## กรณีพิเศษที่ใส่ไว้ในข้อมูลโดยตั้งใจ

ข้อมูลจริงในองค์กรมักไม่สะอาด ชุดข้อมูลฝึกจึงใส่ปัญหาที่พบบ่อยไว้ให้ฝึกตรวจจับ

| กรณี | อยู่ที่ไหน | ฝึกในบทที่ |
|---|---|---|
| `NULL` ในรหัสลูกค้า (ไม่ใช่สมาชิก) | `sales.customer_id` 29 แถว | 6, 8, 19 |
| `NULL` ในส่วนลด (ไม่ได้บันทึก) | `sales.discount_amount` 20 แถว | 8, 19 |
| แถวซ้ำทั้งแถว | `sales.sale_id = 'T0042'` (2 แถว) | 19, 25 |
| รหัสสินค้าที่ไม่มีในตารางสินค้า | `sales.product_id = 'P099'` | 10, 19 |
| จำนวนติดลบ (รับคืน) | `sale_id = 'T0061'` (quantity −2) | 7, 19 |
| จำนวนผิดปกติ | `sale_id = 'T0096'` (quantity 60) | 7, 19 |
| ยอดสุทธิติดลบเพราะส่วนลดมากกว่ายอดสินค้า | `T0044` (−1.00) และ `T0060` (−8.00) | 19 |
| สินค้าที่ไม่มียอดขาย | `products` P011, P012 | 10, 25 |
| สาขาที่ยังไม่มียอดขาย | `stores` S06 (เปิด มิ.ย. 2026) | 10, 12 |
| สาขาเปิดกลางไตรมาส | `stores` S05 (เริ่มขาย มี.ค. 2026) | 14, 21 |
| หมวด/แบรนด์ว่าง | P010 (category), P006 (brand) | 5, 6 |
| วันที่ร้านปิด | ไม่มีการขายวันที่ 1 ม.ค. 2026 | 21 |
| สินค้า 1 ตัวมีหลายโปรโมชัน | `promotions` P002 (2 รายการ) | 10, 20 |
| วันที่/ตัวเลขเป็นข้อความหลายรูปแบบ | `sales_raw` | 17, 18 |

> [!NOTE] ตรวจพบเพิ่มเติมจากเอกสารเดิม
> รายการ `T0044` และ `T0060` มีจำนวนชิ้นเป็นบวก แต่ยอดสุทธิติดลบ เพราะส่วนลด (15 บาท) มากกว่ามูลค่าสินค้า (14 บาท และ 7 บาท) เอกสารเดิมไม่ได้ระบุกรณีนี้ไว้ บทที่ 19 จะสอนวิธีตรวจจับ

## ข้อผิดพลาดที่พบบ่อย

- ลืมเลือก SQL Warehouse หรือ Warehouse ยังเริ่มทำงานไม่เสร็จ จึงรันไม่ได้หรือรอนาน
- ไม่ได้ตั้ง Catalog/Schema เริ่มต้น จึงเจอ `TABLE_OR_VIEW_NOT_FOUND` ทั้งที่ชื่อตารางถูก
- รัน `SELECT *` กับตารางขนาดใหญ่โดยไม่ใส่ `LIMIT` ทำให้ช้าและเปลืองทรัพยากร
- เข้าใจว่าผลลัพธ์จาก `LIMIT` คือแถวแรกของตาราง
- ไม่อ่านชนิดข้อมูลก่อน เช่น วันที่เก็บเป็นข้อความ ทำให้กรองหรือเรียงผิดภายหลัง

> [!MISTAKE] พิมพ์ชื่อตารางผิด หรือไม่ได้เลือก Schema
> Query `SELECT * FROM sale LIMIT 10;` (ตกตัว s) จะได้ Error
>
> ```text
> [TABLE_OR_VIEW_NOT_FOUND] The table or view `sale` cannot be found.
> Verify the spelling and correctness of the schema and catalog.
> ```
>
> วิธีแก้: ตรวจชื่อด้วย `SHOW TABLES` และใส่ชื่อ Schema นำหน้าเมื่อไม่แน่ใจ เช่น `SELECT * FROM sql_training.sales LIMIT 10;`

## อะไรทำให้ Query ช้าบน Databricks

ตารางใน Databricks ส่วนใหญ่เป็น **Delta Table** ที่เก็บข้อมูลเป็นไฟล์จำนวนมากบนที่เก็บข้อมูลบนคลาวด์ ระบบเก็บสถิติของแต่ละไฟล์ไว้ด้วย (เช่น ค่าน้อยสุด–มากสุดของแต่ละคอลัมน์) เวลา Query ทำงาน สิ่งที่ใช้เวลามากที่สุดมักเป็น

| สาเหตุ | อธิบาย |
|---|---|
| **อ่านข้อมูลมากเกินจำเป็น** | อ่านทุกคอลัมน์ทุกไฟล์ ทั้งที่ใช้แค่บางส่วน |
| **ย้ายข้อมูลระหว่างเครื่อง (Shuffle)** | การ JOIN และ GROUP BY ตารางใหญ่ต้องส่งข้อมูลข้ามเครื่องประมวลผล |
| **แถวเพิ่มขึ้นมหาศาล** | JOIN ผิดเงื่อนไขหรือ CROSS JOIN โดยไม่ตั้งใจ |
| **ส่งผลลัพธ์ใหญ่กลับมา** | ดึงหลายล้านแถวกลับมาแสดงหรือดาวน์โหลด |
| **รอเครื่องเริ่มทำงาน** | SQL Warehouse หยุดอยู่ ต้องเริ่มใหม่ (ไม่เกี่ยวกับ Query) |

> [!NOTE] ตารางฝึกเล็กเกินกว่าจะเห็นความต่าง
> ชุดข้อมูลฝึกมีไม่กี่ร้อยแถว ทุก Query จึงเร็วเท่ากัน หลักในบทนี้จะเห็นผลชัดกับตารางจริงที่มีหลายล้านแถวขึ้นไป ให้ฝึกเป็นนิสัยตั้งแต่ตอนนี้

## หลัก 7 ข้อ เขียน Query ให้เร็วและประหยัด

**1. เลือกเฉพาะคอลัมน์ที่ใช้** Delta เก็บข้อมูลแบบแยกคอลัมน์ (Columnar) ระบุคอลัมน์ทำให้อ่านข้อมูลน้อยลงมาก

| ช้ากว่า | เร็วกว่า |
|---|---|
| `SELECT * FROM sales` | `SELECT sale_date, store_id, net_amount FROM sales` |

**2. กรองให้เร็วที่สุดด้วยช่วงวันที่** ใส่เงื่อนไขช่วงเวลาใน `WHERE` เสมอ เพื่อให้ระบบข้ามไฟล์ที่ไม่เกี่ยวข้อง (Data Skipping)

**3. อย่าครอบคอลัมน์ที่ใช้กรองด้วยฟังก์ชัน**

| ช้ากว่า | เร็วกว่า |
|---|---|
| `WHERE YEAR(sale_date) = 2026 AND MONTH(sale_date) = 2` | `WHERE sale_date >= DATE'2026-02-01' AND sale_date < DATE'2026-03-01'` |
| `WHERE CAST(sale_datetime AS DATE) = DATE'2026-02-14'` | `WHERE sale_datetime >= TIMESTAMP'2026-02-14 00:00:00' AND sale_datetime < TIMESTAMP'2026-02-15 00:00:00'` |

ทั้งสองแบบให้ผลเหมือนกัน แต่แบบขวาเทียบคอลัมน์ดิบกับค่าคงที่ ระบบจึงใช้สถิติของไฟล์ตัดไฟล์ที่ไม่เกี่ยวข้องทิ้งได้ตั้งแต่ต้น

**4. สรุปก่อน JOIN เมื่อทำได้** เช่น สรุปยอดรายวันเหลือไม่กี่ร้อยแถว แล้วค่อย JOIN กับ `calendar` ดีกว่า JOIN รายการหลายล้านแถวก่อนแล้วค่อยสรุป (ยังช่วยกัน Fan-out ด้วย)

**5. ใช้ `UNION ALL` แทน `UNION` และอย่าใส่ `DISTINCT` โดยไม่จำเป็น** การตัดแถวซ้ำต้องเรียงหรือเทียบข้อมูลทั้งหมด ซึ่งช้า

**6. ระวัง JOIN ที่ทำให้แถวเพิ่ม** นับแถวก่อน/หลัง JOIN ตรวจว่าไม่มี Fan-out หรือ CROSS JOIN โดยไม่ตั้งใจ

**7. จำกัดผลลัพธ์ที่ดึงกลับมา** ตอนสำรวจใช้ `LIMIT` แต่รู้ไว้ว่า `LIMIT` ช่วยลดการ**ส่ง**ผลลัพธ์ ไม่ได้ช่วยลดการ**อ่าน**เสมอไป ถ้ามี `ORDER BY` หรือ `GROUP BY` ระบบยังต้องอ่านข้อมูลทั้งหมดก่อนจัดเรียง

> [!TIP] ทางเลือกเมื่อไม่ต้องการตัวเลขแม่นยำ 100%
> นับค่าไม่ซ้ำในตารางใหญ่มากด้วย `approx_count_distinct(customer_id)` จะเร็วกว่า `COUNT(DISTINCT customer_id)` มาก แลกกับความคลาดเคลื่อนเล็กน้อย (ค่าเริ่มต้นประมาณ 5%) ใช้กับการสำรวจข้อมูล ไม่ใช้กับตัวเลขที่ต้องรายงานแบบแม่นยำ

## ดูแผนการทำงานด้วย EXPLAIN

`EXPLAIN` แสดงแผนการทำงาน (Physical Plan) ที่ระบบจะใช้ **โดยไม่รัน Query จริง**

```sql
EXPLAIN
SELECT
  store_id,
  SUM(net_amount) AS net_sales
FROM sales
WHERE sale_date >= DATE'2026-03-01'
GROUP BY store_id;
```

แผนอ่านจาก**ล่างขึ้นบน** (ขั้นแรกอยู่ล่างสุด) สิ่งที่ควรมองหา

| สิ่งที่เห็นในแผน | ความหมาย | ดีหรือไม่ |
|---|---|---|
| `PushedFilters` / `DataFilters` ที่มีเงื่อนไขวันที่ | เงื่อนไขถูกใช้ตั้งแต่ตอนอ่านไฟล์ | ดี |
| `ReadSchema` มีเฉพาะคอลัมน์ที่ใช้ | อ่านเฉพาะคอลัมน์ที่จำเป็น | ดี |
| `Exchange` (Shuffle) | ย้ายข้อมูลระหว่างเครื่อง เกิดจาก GROUP BY / JOIN | จำเป็นบ้าง แต่ยิ่งน้อยยิ่งดี |
| `BroadcastHashJoin` | ส่งตารางเล็กไปทุกเครื่อง แล้ว JOIN | ดี สำหรับ JOIN ตารางเล็ก (Dimension) |
| `SortMergeJoin` | เรียงทั้งสองฝั่งแล้ว JOIN | ปกติสำหรับตารางใหญ่สองตาราง |
| `CartesianProduct` / `BroadcastNestedLoopJoin` | จับคู่ทุกแถวกับทุกแถว | ตรวจว่าตั้งใจหรือไม่ อาจลืมเงื่อนไข JOIN |

## Query Profile และ Query History

หลังรัน Query ใน SQL Editor สามารถเปิด **Query History** แล้วเลือก Query เพื่อดู **Query Profile** (ตามสิทธิ์ที่ได้รับ) ซึ่งแสดงแบบกราฟิกว่าแต่ละขั้นใช้เวลาเท่าไร อ่านกี่แถว และอ่านข้อมูลกี่ไบต์

**ตัวเลขที่ควรดู**

- **Rows read / Bytes read** อ่านข้อมูลมากกว่าที่คาดหรือไม่ (ถ้าใช่ อาจลืมกรองวันที่)
- **Files pruned / Files read** ระบบข้ามไฟล์ได้กี่ไฟล์จากเงื่อนไข
- **ขั้นที่ใช้เวลามากที่สุด** มักเป็น JOIN หรือ Aggregate ที่ใหญ่
- **Rows output ของ JOIN** มากกว่าฝั่ง Input มากหรือไม่ (สัญญาณ Fan-out)

> [!DATABRICKS] สิ่งที่ระบบช่วยให้อัตโนมัติ
> SQL Warehouse ของ Databricks มีความสามารถหลายอย่างที่ช่วยเรื่องความเร็วโดยเราไม่ต้องทำอะไร เช่น **Photon** (เครื่องมือประมวลผลที่เร็วขึ้น), **Adaptive Query Execution** (ปรับแผนระหว่างรัน) และ**การ Cache ผลลัพธ์** (รัน Query เดิมซ้ำกับข้อมูลที่ไม่เปลี่ยนจะได้ผลเร็วมาก) การจัดวางข้อมูล เช่น Partition, Z-Order หรือ Liquid Clustering เป็นหน้าที่ของทีม Data Engineer ถ้า Query สำคัญช้าเป็นประจำให้ส่ง Query Profile ไปปรึกษาทีมนั้น

## ประหยัดค่าใช้จ่ายของ SQL Warehouse

- ใช้ Warehouse ตามที่ทีมกำหนด ไม่เปิด Warehouse ขนาดใหญ่เองโดยไม่จำเป็น
- ไม่รัน Query หนักซ้ำ ๆ เพื่อดูผลเดิม ให้ Export ผลหรือสร้าง View/ตารางสรุปตามขั้นตอนขององค์กร
- Dashboard ที่ Refresh บ่อยควรใช้ Dataset ที่สรุปแล้ว (Grain เหมาะสม) ไม่ใช่ข้อมูลรายการดิบทั้งหมด
- ยกเลิก (Cancel) Query ที่รันนานผิดปกติ แล้วตรวจหาสาเหตุ แทนการรอ

## สรุปและตรวจความเข้าใจ

| หลัก | ทำอย่างไร |
|---|---|
| อ่านน้อย | เลือกคอลัมน์ กรองช่วงวันที่ด้วยคอลัมน์ดิบ |
| ย้ายข้อมูลน้อย | สรุปก่อน JOIN, JOIN กับ Dimension ที่ Key ไม่ซ้ำ |
| แถวไม่ระเบิด | ตรวจ Fan-out, หลีกเลี่ยง CROSS JOIN ที่ไม่ตั้งใจ |
| ส่งกลับน้อย | ใช้ `LIMIT` ตอนสำรวจ ส่งเฉพาะ Grain ที่จำเป็นให้ Power BI |
| ตรวจได้ | อ่าน `EXPLAIN` และ Query Profile |

> [!CHECK] ลองตอบ
> Query ใดน่าจะเร็วกว่ากันบนตาราง `sales` ขนาด 500 ล้านแถว เพราะอะไร
> (ก) `SELECT * FROM sales WHERE DATE_FORMAT(sale_date, 'yyyy-MM') = '2026-02'`
> (ข) `SELECT sale_id, store_id, net_amount FROM sales WHERE sale_date >= DATE'2026-02-01' AND sale_date < DATE'2026-03-01'`

:::answer ดูคำตอบ
(ข) เร็วกว่า ด้วยเหตุผล 2 ข้อ: (1) เลือกเฉพาะ 3 คอลัมน์ ระบบอ่านข้อมูลน้อยกว่าการอ่านทุกคอลัมน์ (2) เทียบคอลัมน์ `sale_date` ดิบกับช่วงวันที่คงที่ ระบบใช้สถิติของไฟล์ข้ามไฟล์ที่ไม่มีข้อมูลเดือนกุมภาพันธ์ได้ ส่วน (ก) ต้องแปลงวันที่ทุกแถวเป็นข้อความก่อนเทียบ จึงข้ามไฟล์ไม่ได้
:::
